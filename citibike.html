Batch Pipeline · 12 Months · Every Trip Checked

A year of Citi Bike, checked before charted.

Citi Bike publishes every trip it serves, millions per month, far too many to fetch in a browser. A local DuckDB pipeline downloads the monthly files, tests every row against documented rules, and ships only small aggregates to this page. The first tab shows exactly what was checked and what was removed. The second shows how New York actually rides.

Every rule, every count

Each row of the source data is tested against these rules before it can reach a chart. Found counts can overlap when a trip trips several rules; the removed total is deduplicated, so checked minus removed equals kept exactly.

Removal rate by month

Share of each month's rows removed by the rules above. A stable rate across months is itself a check: a spike would mean the feed changed, not the city.

Missing values by column

Share of rows with a null in each source column, before cleaning. Missing end stations are real behavior, a bike that never docked, so those rows are kept and flagged instead of dropped.

Sample rows, kept and removed

150 randomly sampled kept trips plus up to 50 removed rows, each labeled with the rule that caught it. Click a header to sort. Missing values show as null instead of being hidden.

Data dictionary: all 13 source columns

Everything the source files publish, whether this page uses it or not. Source: Citi Bike system data.

Read this like a statistician: these are trips, not riders; one commuter is 500 rows a year. Lyft filters the rawest errors before publishing, staff service trips are already excluded, and durations cap at exactly 1,500 minutes, so what looks like a clean feed still carries dock tests, GPS glitches, and bikes that never came home. The rules above make those visible instead of pretending they are not there.

Every day for a year

Daily trip counts from the kept rows. The winter dip is gradual; the hole in late February is not. Citi Bike shut the whole system down for the 2026 blizzard, and the data says so with a zero.

The shape of a year

Monthly totals with the median trip duration overlaid. Ridership roughly halves in winter; trip length barely moves, because commutes do not get longer just because it is June.

When New York rides

Trips by hour and weekday. Members paint the two commute stripes at 8 am and 5 to 6 pm; casual riders draw one warm weekend blob in the afternoon.

How long a trip lasts

Share of each group's trips by duration. Members cluster hard under 15 minutes; casual riders ride longer and pay for it.

The busiest docks

Top 30 stations by departures, colored by member share. Hover for arrivals; a big gap between the two means rebalancing trucks are doing the rest.

What the aggregates hide: station coordinates in the source are per-trip GPS fixes, not surveyed dock locations, which is why the pipeline validates them against a bounding box instead of trusting them. And a trip says nothing about a route; only the endpoints are recorded.

How this dashboard works (for the technically curious)

Unlike the live dashboards on this site, this page cannot fetch its source: Citi Bike's historical trip files are monthly zips totaling about 8 GB per year, published to a public S3 bucket. A local Python script (scripts/citibike/prep.py) downloads each month, converts it to Parquet, runs every cleaning rule as DuckDB SQL, and writes the small JSON aggregates this page renders. Raw files never leave the laptop; only the aggregates, about 200 KB, are committed.

The quality tab is generated from the same pipeline run that produced the charts, so the counts you see are the counts that happened. Charts are Plotly.js; tables are the same vanilla renderer used across this site. The tab renders lazily because Plotly mis-sizes charts drawn into hidden elements, the kind of detail you learn by shipping.
